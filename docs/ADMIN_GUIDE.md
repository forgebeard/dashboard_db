# Руководство администратора RED Virt Analytics

## 1. Назначение документа

Это руководство предназначено для специалиста, который устанавливает и обслуживает RED Virt Analytics на рабочей станции инженера технической поддержки.

В документе описаны:

- подготовка рабочей станции;
- установка Docker и PostgreSQL;
- восстановление дампа oVirt Engine;
- первый запуск приложения;
- изменение подключения;
- запуск, остановка и обновление;
- просмотр журналов;
- устранение типовых проблем.

Работа с интерфейсом и диагностическими разделами описана в [руководстве пользователя](USER_GUIDE.md).

## 2. Схема работы

RED Virt Analytics запускается в Docker-контейнере и подключается к PostgreSQL по сети.

```text
Браузер пользователя
        │
        │ http://localhost:8502
        ▼
Контейнер RED Virt Analytics
        │
        │ host.docker.internal:5432
        ▼
PostgreSQL на рабочей станции
        │
        ▼
Восстановленный дамп oVirt Engine
```

Python на рабочую станцию устанавливать не требуется.

## 3. Требования

### Поддерживаемые рабочие станции

- РЕД ОС 8;
- Windows с Docker Desktop.

### Необходимые компоненты

1. Docker и Docker Compose.
2. PostgreSQL с восстановленным дампом oVirt Engine.
3. Архив RED Virt Analytics.
4. Свободный локальный TCP-порт `8502`.
5. Учётная запись PostgreSQL с доступом на чтение к восстановленной базе.

Инструкции по подготовке компонентов:

- Docker на РЕД ОС 8 — [DOCKER_RED_OS.md](DOCKER_RED_OS.md);
- Docker Desktop на Windows — [DOCKER_WINDOWS.md](DOCKER_WINDOWS.md);
- установка PostgreSQL — [ДОБАВИТЬ ССЫЛКУ];
- восстановление дампа oVirt Engine — [ДОБАВИТЬ ССЫЛКУ].

## 4. Требования безопасности

- Используйте только локально восстановленную копию базы данных.
- Не подключайте RED Virt Analytics напрямую к продуктивной базе oVirt Engine.
- Не передавайте архив вместе с файлом `.env`, журналами или дампами другого пользователя.
- Храните дампы в каталоге с ограниченным доступом.
- Не публикуйте порт PostgreSQL и порт приложения во внешние сети без отдельного согласования.
- Для постоянной эксплуатации рекомендуется отдельная роль PostgreSQL с правами только на чтение.
- Приложение рассчитано на одного инженера на рабочей станции. Порт контейнера публикуется только на `127.0.0.1`. Файл `logs/sql_history.json` общий для всех вкладок и сессий этого экземпляра (записи сгруппированы по имени базы).

Приложение дополнительно открывает соединения PostgreSQL в режиме `read-only`, ограничивает размер выборки и время выполнения запросов. Эти ограничения не заменяют корректную настройку прав пользователя PostgreSQL.

## 5. Подготовка PostgreSQL

### 5.1 Установите PostgreSQL

Установите поддерживаемую версию PostgreSQL в соответствии с внутренней инструкцией:

[ДОБАВИТЬ ССЫЛКУ НА ИНСТРУКЦИЮ ПО УСТАНОВКЕ POSTGRESQL]

После установки проверьте состояние службы.

Пример для Linux:

```bash
systemctl status postgresql-15
```

Название службы и путь к данным зависят от установленной версии и дистрибутива.

### 5.2 Восстановите дамп

Создайте отдельную базу данных и восстановите в неё дамп oVirt Engine.

Подробная инструкция:

[ДОБАВИТЬ ССЫЛКУ НА ИНСТРУКЦИЮ ПО ВОССТАНОВЛЕНИЮ ДАМПА]

Рекомендуемое имя базы:

```text
engine
```

Допускается другое имя. Его потребуется указать в параметре `DB_NAME` при первом запуске приложения.

После восстановления убедитесь, что база доступна локально. Например:

```bash
psql -h localhost -p 5432 -U postgres -d engine -c "SELECT 1;"
```

### 5.3 Пользователь только для чтения

Если политикой эксплуатации предусмотрено создание отдельной роли, выполните команды от имени администратора PostgreSQL. Замените имя базы и пароль своими значениями.

```sql
CREATE ROLE ovirt_reader LOGIN PASSWORD '<СЛОЖНЫЙ_ПАРОЛЬ>'
    NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT;

GRANT CONNECT ON DATABASE engine TO ovirt_reader;
```

Подключитесь к базе `engine` и выдайте права на схему и таблицы:

```sql
GRANT USAGE ON SCHEMA public TO ovirt_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO ovirt_reader;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO ovirt_reader;
```

Если приложение должно видеть список всех восстановленных баз, этой роли также потребуются права `CONNECT` и `SELECT` для каждой анализируемой базы.

При первом запуске укажите:

```text
DB_USER=ovirt_reader
```

Использование отдельной роли рекомендуется, но текущие скрипты допускают подключение пользователем `postgres`.

## 6. Установка приложения

### 6.1 Распакуйте архив

Распакуйте полученный архив в отдельный каталог.

Пример для Linux:

```text
/opt/red-virt-analytics
```

Если установка в `/opt` выполняется без административных прав, выберите каталог внутри домашнего каталога пользователя.

Пример для Windows:

```text
C:\REDVirtAnalytics
```

Не запускайте приложение непосредственно из ZIP-архива.

### 6.2 Проверьте содержимое каталога

В пользовательской поставке должны присутствовать как минимум:

```text
src/
.streamlit/
Dockerfile
docker-compose.yml
start.sh
start.bat
requirements.txt
.env.example
README.md
docs/
LICENSE
```

Руководства пользователя и администратора, а также инструкции по установке Docker находятся в каталоге `docs/`.

Файл `.env` может отсутствовать до первого запуска — это нормально.

### 6.3 Запустите приложение на Linux

Перейдите в каталог приложения:

```bash
cd /путь/к/red-virt-analytics
```

Разрешите выполнение скрипта, если это требуется:

```bash
chmod +x start.sh
```

Запустите:

```bash
./start.sh
```

### 6.4 Запустите приложение на Windows

Откройте `cmd` или PowerShell и перейдите в каталог приложения:

```cmd
cd C:\REDVirtAnalytics
```

Запустите:

```cmd
start.bat
```

### 6.5 Укажите параметры подключения

При первом запуске скрипт последовательно запросит параметры PostgreSQL.

| Параметр | Значение по умолчанию | Описание |
|---|---|---|
| `DB_HOST` | `host.docker.internal` | PostgreSQL на той же рабочей станции, что и Docker |
| `DB_PORT` | `5432` | Порт PostgreSQL |
| `DB_NAME` | `engine` | Имя базы с восстановленным дампом |
| `DB_USER` | `postgres` | Пользователь PostgreSQL |
| `DB_PASSWORD` | — | Пароль пользователя, обязателен |

Скрипт создаст файл `.env`, соберёт Docker-образ и запустит контейнер `red-virt-analytics`.

На Windows `start.bat` записывает пароль в `.env` командой `echo`. Символы `&`, `%` и `!` в пароле могут исказить файл. Если пароль содержит эти символы, создайте `.env` вручную по образцу `.env.example`.

Не добавляйте `.env` в архив, систему контроля версий или обращение в поддержку без предварительного удаления пароля.

### 7.1 Проверьте контейнер

```bash
docker compose ps
```

Ожидается запущенный сервис `red-virt-analytics`. После завершения healthcheck его состояние должно стать `healthy`.

### 7.2 Проверьте журнал запуска

```bash
docker compose logs --tail=100
```

В журнале не должно быть повторяющихся ошибок подключения или аварийного завершения Streamlit.

### 7.3 Откройте интерфейс

Перейдите в браузере по адресу:

**http://localhost:8502**

Убедитесь, что:

1. открывается боковая панель приложения;
2. отображается список доступных баз;
3. можно выбрать базу с дампом;
4. раздел «Хосты» загружается без ошибки подключения.

## 8. Управление приложением

Все команды выполняются из каталога, содержащего `docker-compose.yml`.

### Запуск или пересборка

Linux:

```bash
./start.sh
```

Windows:

```cmd
start.bat
```

### Просмотр состояния

```bash
docker compose ps
```

### Просмотр журналов

```bash
docker compose logs -f
```

Для выхода из режима просмотра нажмите `Ctrl+C`. Контейнер при этом продолжит работу.

```bash

```

```bash
docker compose down
```

## 9. Изменение подключения

Для повторного ввода параметров используйте флаг `-r`.

Linux:

```bash
./start.sh -r
```

Windows:

```cmd
start.bat -r
```

Скрипт удалит текущий `.env`, запросит параметры заново и пересоберёт приложение.

Перед перенастройкой убедитесь, что у вас есть пароль к новой базе.

## 10. Расположение данных приложения

В каталоге приложения используются:

| Путь | Содержимое | Рекомендация |
|---|---|---|
| `.env` | Параметры подключения и пароль PostgreSQL | Не передавать третьим лицам |
| `logs/app.log` | Журнал приложения | При передаче проверить конфиденциальные данные |
| `logs/sql_history.json` | История SQL-запросов по базам | При необходимости очистить перед передачей |
| PostgreSQL data directory | Восстановленные базы | Резервировать средствами PostgreSQL |

Контейнер работает от непривилегированного пользователя `appuser` (uid `1000`). Каталог `logs` на рабочей станции должен быть доступен этому uid на запись, иначе не появятся `app.log` и история SQL. При необходимости:

```bash
mkdir -p logs
sudo chown -R 1000:1000 logs
```

Команда для Linux/РЕД ОС: обычный пользователь не может сменить владельца на uid `1000`. `chown` меняет владельца уже существующих файлов в `logs`.

В `docker-compose.yml` том указан как `./logs:/app/logs:Z`: суффикс `:Z` нужен на РЕД ОС с SELinux (приватная переразметка). На системах без SELinux Docker обычно игнорирует его.

Проверка записи: выполните любой `SELECT` в SQL-редакторе и убедитесь, что на хосте обновляются файлы `logs/app.log` и `logs/sql_history.json`.

В пользовательской поставке `docker-compose.yml` монтирует только `logs`. Код и версия берутся из образа. Файл `docker-compose.override.yml` есть только в репозитории разработки и подключает `src`, `.streamlit` и `VERSION` для hot-reload; в zip-архив он не входит.

Чтобы показать полный traceback неожиданной ошибки в интерфейсе, задайте в `.env` переменную `DEBUG=true` и пересоздайте контейнер. Без неё в UI выводится краткое сообщение с кодом события, подробности пишутся в `logs/app.log`.

Удаление контейнера не удаляет каталог `logs`, поскольку он подключён к контейнеру с рабочей станции.

## 11. Обновление приложения

Обновление выполняется заменой файлов из нового архива.

### Рекомендуемый порядок

1. Закройте работу в интерфейсе.
2. Остановите приложение:

   ```bash
   docker compose down
   ```

3. Сохраните резервную копию:

   - файла `.env`;
   - каталога `logs`, если журналы необходимо сохранить.

4. Распакуйте новую версию в новый каталог.
5. Перенесите `.env` из предыдущей версии в новый каталог.
6. Не переносите старые `src`, `Dockerfile`, `docker-compose.yml` и `requirements.txt` поверх новой версии.
7. Запустите новый вариант:

   **Linux:**

   ```bash
   ./start.sh
   ```

   **Windows:**

   ```cmd
   start.bat
   ```

8. Проверьте состояние контейнера и открытие интерфейса.
9. После успешной проверки старый каталог можно удалить.

Восстановленная база PostgreSQL при обновлении приложения не изменяется.

## 12. Подключение контейнера к PostgreSQL

### 12.1 PostgreSQL на той же рабочей станции

Используйте:

```text
DB_HOST=host.docker.internal
```

Внутри контейнера `localhost` указывает на сам контейнер, а не на операционную систему рабочей станции. Поэтому указывать `DB_HOST=localhost` для PostgreSQL на хосте обычно нельзя.

### 12.2 PostgreSQL на удалённом сервере

Укажите IP-адрес или DNS-имя сервера:

```text
DB_HOST=192.168.1.50
```

На сервере PostgreSQL должны быть разрешены подключения с IP-адреса рабочей станции, на которой работает Docker.

### 12.3 Контейнер не видит локальный PostgreSQL на Linux

Частая причина: PostgreSQL слушает только `127.0.0.1`, а контейнер подключается через интерфейс Docker bridge.

Проверьте прослушиваемые адреса:

```bash
ss -tlnp | grep 5432
```

Проверьте значение в PostgreSQL:

```sql
SHOW listen_addresses;
```

Настройка зависит от сетевой политики рабочей станции. Универсальный, но широкий вариант:

```text
listen_addresses = '*'
```

> `listen_addresses='*'` заставляет PostgreSQL слушать все сетевые интерфейсы. Перед применением ограничьте доступ средствами `pg_hba.conf` и локального файрвола.

После изменения перезапустите соответствующую службу PostgreSQL.

Пример строки `pg_hba.conf` для типичных адресов Docker:

```text
host    all    all    172.16.0.0/12    md5
```

> Диапазон `172.16.0.0/12` широкий и может включать адреса LAN или VPN. Предпочтительно определить фактическую подсеть Docker и разрешить только её.

Посмотреть сети Docker:

```bash
docker network ls
docker network inspect bridge
```

После изменения `pg_hba.conf` перезагрузите конфигурацию PostgreSQL.

Пример для PostgreSQL 15 на Linux:

```bash
sudo systemctl reload postgresql-15
```

Название службы может отличаться.

## 13. Устранение проблем

### Не появляются `logs/app.log` или `logs/sql_history.json`

Контейнер пишет журналы от uid `1000` в каталог `logs` на рабочей станции.

- Проверьте владельца: `ls -ld logs` — каталог должен быть доступен uid/gid `1000`. На Linux/РЕД ОС: `sudo chown -R 1000:1000 logs` (меняет владельца уже лежащих файлов журнала).
- На РЕД ОС с SELinux том должен быть с суффиксом `:Z` (уже задан в `docker-compose.yml`). После правки Compose пересоздайте контейнер: `docker compose up -d`.
- Выполните запрос в SQL-редакторе и снова посмотрите файлы на хосте.

### Приложение не открывается по адресу `localhost:8502`

Проверьте:

```bash
docker compose ps
docker compose logs --tail=100
```

Возможные причины:

- Docker не запущен;
- контейнер завершился с ошибкой;
- порт `8502` занят другим процессом;
- образ не собрался;
- команда выполнялась не из каталога приложения.

Проверка порта на Linux:

```bash
ss -tlnp | grep 8502
```

Проверка порта на Windows:

```cmd
netstat -ano | findstr :8502
```

### Контейнер постоянно перезапускается

Посмотрите журнал:

```bash
docker compose logs --tail=200
```

Затем проверьте наличие обязательных файлов:

```text
.env
src/app.py
.streamlit/config.toml
requirements.txt
```

### Ошибка подключения к PostgreSQL

Проверьте:

1. запущена ли служба PostgreSQL;
2. правильны ли `DB_HOST`, `DB_PORT`, `DB_USER` и `DB_PASSWORD`;
3. существует ли база, указанная в `DB_NAME`;
4. разрешены ли сетевые подключения в `postgresql.conf` и `pg_hba.conf`;
5. не блокирует ли соединение локальный файрвол.

Для повторного ввода параметров выполните:

```bash
./start.sh -r
```

или на Windows:

```cmd
start.bat -r
```

### Ошибка `password authentication failed`

Причина — неверный пароль либо неподходящий метод аутентификации в `pg_hba.conf`.

Проверьте подключение теми же реквизитами напрямую к PostgreSQL. Не публикуйте пароль в снимках экрана и журналах обращения.

### Ошибка `connection refused`

PostgreSQL не принимает соединение на указанном адресе и порту.

Проверьте:

- состояние службы;
- `listen_addresses`;
- порт PostgreSQL;
- адрес `DB_HOST`;
- правила файрвола.

### Список баз не загружается

Пользователь PostgreSQL должен иметь возможность подключиться к служебной базе `postgres` или `template1`, чтобы приложение получило список доступных баз.

Также проверьте журнал приложения и параметры `.env`.

### Выбранная база открывается, но некоторые разделы показывают ошибки

Возможные причины:

- дамп восстановлен не полностью;
- версия схемы Engine пока не поддерживается модулем;
- в дампе отсутствует необязательная таблица;
- у пользователя PostgreSQL недостаточно прав;
- запрос превысил установленный таймаут.

Проверьте версию Engine в разделе «Системные» и сведения о совместимости в разделе «Справочник».

### Запрос прерван по таймауту

По умолчанию запросы ограничиваются 30 секундами. Для изменения значения добавьте в `.env`, например:

```env
STATEMENT_TIMEOUT_MS=60000
```

После изменения пересоздайте контейнер, чтобы новое значение из `.env` попало в его окружение:

```bash
docker compose up -d --force-recreate
```

Не увеличивайте таймаут без необходимости. Сначала сузьте фильтры или упростите SQL-запрос.

### Недостаточно места на диске

Проверьте использование Docker:

```bash
docker system df
```

Не удаляйте Docker volumes и каталоги PostgreSQL без проверки их содержимого. Очистка Docker должна выполняться по принятому в организации регламенту.

## 14. Сбор диагностической информации

Перед обращением к разработчику соберите:

```bash
docker compose ps
docker compose logs --tail=300
docker version
docker compose version
```

Также укажите:

- операционную систему;
- версию PostgreSQL;
- имя выбранной базы без пароля;
- версию Engine, если она определяется приложением;
- раздел и действие, при котором возникла ошибка;
- точное время возникновения проблемы.

Перед передачей журналов проверьте наличие конфиденциальных сведений. Не прикладывайте `.env` и дамп базы без отдельного согласования.

## 15. Удаление приложения

1. Остановите контейнер:

   ```bash
   docker compose down
   ```

2. Убедитесь, что контейнер отсутствует:

   ```bash
   docker compose ps
   ```

3. Удалите каталог приложения, если больше не нужны `.env`, журналы и история SQL.

4. Восстановленную базу PostgreSQL удаляйте отдельно и только после подтверждения, что она больше не требуется.

Удаление каталога RED Virt Analytics не удаляет PostgreSQL и его базы данных.
